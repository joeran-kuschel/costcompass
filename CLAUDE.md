# Costcompass (Nuxt)

A web app to track household expenses (rent, insurance, appliances, etc.) with an optional business category. On top of the tracked costs, a rate calculator answers: "I have costs of X, how much do I have to earn?" (required annual revenue and minimum hourly rate).

## How we work

- I write most of the code myself and make my own decisions on components, libraries and structure.
- Claude's role is to **guide**: explain concepts, propose next steps, point out options and trade-offs, review my code, help debug.

### Fixed rules

- **Every feature goes into its own branch.** Nothing is built or committed directly on `main`; the branch is merged through a pull request.
- **Documentation comes before the pull request.** A pull request is only created once the documentation for its feature is written (in `documentation/`, in `frontend/` or `backend/`). The pull request text names the documentation that belongs to it.

## Scope of the first version

- Cost tracking is the main feature: recurring costs (rent, insurance) and one-off purchases (appliances), with categories and an optional business flag
- Totals per period and category, household versus business
- Rate calculator comes later as a separate feature that takes the tracked costs as input
- No accounts yet (single user)
- Data stored in PostgreSQL via Nuxt server routes
- Runs on Kubernetes (Docker Desktop's built-in cluster)
- Bilingual UI: English is the default, German is the second language (`@nuxtjs/i18n`, all text in locale files)
- Income tax for the rate calculator starts as a simple flat rate; the exact German tariff (§32a EStG) comes later as its own step

## Architecture

- **Calculation core:** pure TypeScript functions (inputs in, results out) in `shared/`, covered by Vitest tests running in the Nuxt environment (`@nuxt/test-utils`). Types in `shared/types/`, functions in `shared/utils/`, both auto-imported. No database access and no Vue state in the functions. Can run on client and server.
- **Frontend:** `app/` (pages, components, composables). Only collects input, displays results, talks to the API.
- **API:** Nitro server routes in `server/api/`, the only layer that touches the database.
- **Database:** PostgreSQL, accessed through an ORM or query builder with versioned migrations.
- **i18n:** locale files for `en` and `de`; no hard-coded UI text.
- **Configuration:** connection settings via `runtimeConfig`, overridden by environment variables (e.g. `NUXT_DATABASE_URL`), so the same image runs locally and in the cluster.

## Cost tracking logic

1. Recurring costs: amount plus interval (monthly, yearly, possibly quarterly), normalized to one period
2. One-off purchases: date and price, counted fully in the year of purchase (spreading over a lifespan is parked, see decisions)
3. Categories (housing, insurance, appliances, etc.) and an optional business flag
4. Totals per period and category, household versus business
5. Monthly overview: `monthlyTotals(recurring, purchases, year)` returns the true cost of each of the 12 months (not an average); purchases land in the month of their date, monthly recurring costs count in every month
6. Monthly breakdown: `costsInMonth(recurring, purchases, year, month)` returns the list of costs that occur in one month (recurring first, then purchases). It is generic, so stored items keep their `id` (rows need a key), so the UI can show recurring costs and purchases clearly apart. `monthlyTotals` and `totalMonthlyCost` are consistent with it (a month's total is the sum of its list).
7. Annual summary: `annualSummary(recurring, purchases, year)` returns `{ total, household, business, averagePerMonth }` for the dashboard tiles. `business` is the total of the business costs and `household` is `total - business`, so household plus business equals the total by construction; the average is the total divided by 12, not rounded.
8. Category breakdown: `categoryBreakDown(recurring, purchases, year)` returns one `{ category, total, share }` per category, sorted by total, largest first. `share` is the total relative to the largest category (between 0 and 1), so the bars can be sized directly; categories without costs are included with 0. Equal totals keep the order of `CATEGORIES`.
9. Cost split: `splitPercentages(summary)` turns an `AnnualSummary` into whole percentages for household and business. The business share is rounded and household is `100 - business`, so the two always add up to exactly 100; a total of 0 gives 0 and 0 instead of NaN.
10. Month breakdown: `monthBreakdown(recurring, purchases, year)` returns one `{ month, total, share }` per month in calendar order (January to December, no sorting). `share` is the total relative to the largest month (between 0 and 1); with no costs at all every share is 0 instead of NaN.
11. Month change: `monthChange(recurring, purchases, year, month)` returns `{ current, previous, percent }`: the totals of the month and of the month before it (January compares with December of the previous year, which matters for purchases) and the signed whole-number change in percent (negative means less). `percent` is `null` when the previous month cost nothing, so the UI never divides by zero. "Today" is not read in the core, the caller passes year and month.
12. Month neighbours: `monthNeighbours({ year, month }, validYears)` returns the previous and the next month as `{ year, month }` (January goes back to December of the previous year, December on to January of the next). A neighbour in a year that is not in `validYears` is `null`, so the month page can hide that link; the valid years are the years with data plus the current year (`availableYears`). It does not bridge a gap between valid years.
13. Month groups: `groupMonthCosts(costs)` splits the result of `costsInMonth` by kind into `recurring` and `purchases`, each with a subtotal, plus the `total`. It is generic (`MonthGroups<R, P>`), so stored items keep their `id`; a group without entries is an empty list with a subtotal of 0. The total is added in the same order as `totalMonthlyCost`, so it equals the matching entry of `monthlyTotals`.

## Rate calculator (later)

1. Tracked costs as the starting point: household and business costs, annual
2. Social security as a freelancer (health and long-term care insurance, retirement provision, optional unemployment insurance)
3. Income tax on the profit, so the net need is grossed up to a required profit (VAT is passed through and stays out)
4. Buffer and savings (reserves for quiet months, investments)
5. Billable capacity: working days minus vacation, sick days and public holidays, minus the non-billable share (acquisition, admin, learning)
6. Result: required annual revenue ÷ billable hours = minimum hourly rate, with scenarios (e.g. different utilization levels)

1. `/` **Dashboard** (`pages/index.vue`, shell exists): sections are a year selector, annual total, household versus business split, totals per category and the 12 monthly totals. The shell is there: the `h1`, both cost lists fetched with `useFetch` and `lazy: true` (same URLs as `/costs`, so both pages share the cached data), and three states decided by computed flags: `loading` (a list has not arrived yet; a `role="status"` text), `failed` (either request failed; a `UAlert` with `role="alert"` and a retry button that refreshes both lists) and `empty` (no costs at all; a hint and a link to `/costs`). The first section is built: a "Summary for <year>" section (`h2`, labelled with `aria-labelledby`) with four `UCard` tiles (annual total, household, business, average per month) from `annualSummary` in `shared/utils/costs.ts`, shown in whole euros by the `useMoney()` composable. The year comes from `useYear()` (see Decisions), chosen with a `YearSelect` inside the loaded content, just above the summary section; it is not shown while loading, on an error or on the empty screen. The "This month" card, its list and the highlighted month of the chart always use today (`currentYear`), whatever year is selected. The second section is "Costs by category in <year>": a `UCard` with a `ul` of rows from `categoryBreakDown`, each row with a `CategoryBadge` (36 px), the translated name, the amount in whole euros and a hand-built bar whose width is the category's share of the largest one. The bar and its track are `aria-hidden`, so a row reads as name and amount; on narrow screens the bar moves to its own line below name and amount. After the categories sits "Household versus business in <year>": one stacked bar (a `role="img"` with a translated `aria-label`, segments sized by `splitPercentages`, no segment at all for a part of 0%) and a text legend with both percentages, so colour is not the only carrier; household uses the primary and business the secondary colour token. With no costs in the year the bar stays an empty track and the legend says 0%. At the top sits the "This month" card (`aria-labelledby`, `UCard`): "This month, <month> <year>" (localized with `Intl`), the month's total in whole euros and a comparison with the previous month from `monthChange`. The direction is in the words ("50% more than September", "less", "Same as", or a neutral text without a percentage when the previous month cost nothing); the trending icon is decoration (`aria-hidden`). Below the comparison sits the list of the month's costs (`costsInMonth`, a `ul` with an accessible name "Costs in <month>"): recurring costs first, then purchases, no cut-off, each row with the name, a text badge for the kind (and the `BusinessBadge` for business costs) and the amount in whole euros. A month without costs shows a text and an "Add cost" button instead of the list; the button calls `openAdd()` like the add tile. At the end of the card sits the "View <month year>" link (#19, a real link to `monthPath(currentYear, currentMonth)`, so it always leads to today's month, whatever year is selected; it also shows when the month has no costs). Under the card sits the "Add a cost" tile (#20): a heading, a one-line hint and an "Add cost" button that calls `openAdd()` from `useCostDialog()`; the dialog is the layout's, the same form as on `/costs`. After a save the layout refreshes both lists and closes the dialog, so the card, tiles and bars update. The last section is "Costs per month in <year>": a `UCard` with an `ol` of 12 columns from `monthBreakdown`, each a hand-built vertical bar whose height is the month's share of the largest one (a month without costs keeps a thin baseline, `min-h-0.5`). Every item carries a visually hidden text (`sr-only`, "January: €800", from `Intl` month names in the active language), the bar and the short label ("Jan") are `aria-hidden`, the bar has a hover `title`, and the current month's label is bold so the highlight is not colour alone. Every item is a link (`NuxtLink`) to the month page of that month in the selected year (`monthPath`, two-digit month); the hidden text is the link's name, the bar and the label stay `aria-hidden`, and a keyboard focus shows an outline. The columns are at least 24 px wide (`minmax(1.5rem,1fr)`), and the chart scrolls sideways (`overflow-x-auto`) on screens where twelve of them do not fit, so the targets stay big enough on a phone; the `li` has no layout of its own, so the link fills the column. Views that are not pages:

- **Add/edit form:** one modal (`UModal`, chosen over a slide-over for mobile) rendered once by `layouts/default.vue`, not its own routes and not one per page. Its state lives in `useCostDialog()` (`useState`, not provide/inject): the dashboard, the sidebar's "Add cost" button, `/costs` (edit) and the month pages call `openAdd(month?)` or `openEdit(cost)`; each resets the other value, `close()` clears all three, so nothing leaks into the next dialog. The title is "Add cost" or "Edit <name>"; the layout passes `cost` and `month` to `CostForm` and calls `close()` when the modal closes (X, backdrop, Escape) and on `cancel`. Groundwork for a sidebar (#53) and a floating add button (#55), which only have to call `openAdd()`. One form component (`components/CostForm.vue`) for adding and editing both kinds of cost. It takes an optional `cost` prop (`Stored<Cost>`): when set, the form is pre-filled once, the kind radio group is disabled (a cost cannot change its kind), the submit button says "Save" and submit sends a `PATCH` to `/api/<resource>/<id>` instead of a `POST`. A Cancel button emits `cancel` and the layout closes the dialog, which clears the state, so the next "Add cost" starts empty. Built with `UForm` and the Zod schemas (the schema switches with the kind switch), with labelled fields. On submit it POSTs `event.data` (already stripped by Zod) to the matching route and emits `saved`; the layout refreshes both lists (`retry` of `useCostLists()`) and closes the dialog. If the request fails, a toast (`useToast`, text from `form.error`) is shown and the modal stays open with the entered values. A closed modal unmounts its content, so the form starts empty each time. The dialog can pass an optional `month` prop (`{ year, month }`, set when the month page calls `openAdd(monthRef)`): the form then starts a purchase on the first day of that month, limits the date field to that month with `min` and `max` and names the month in a hint ("Pre-filled with October 2026. Pick the day."), and starts a yearly or quarterly cost with that month as `dueMonth`, which stays free to change. The first and last day come from `monthDateRange` in `shared/utils/dates.ts` (UTC, leap years included). The browser limits the date field, the Zod schema does not, so the API still accepts a purchase on any day. The defaults are read once when the form is created, like the `cost` prefill, and an edited cost keeps its own values. Without the prop the form is unchanged, which is what the dashboard and `/costs` use (`openAdd()`).

## Decisions made

- Cost model: a shared base `CostItem` (name, amount, category, business) in `shared/types/calculation.ts`; `RecurringCost` extends it with an interval (monthly, yearly), `Purchase` extends it with a date (ISO string, `YYYY-MM-DD`)
- Category: a fixed list, `CATEGORIES` as a `const` array with `Category` derived from it. Ids are English; display names come from the locale files. The database stores the category as text (optionally with a check or enum), and the server validates against `CATEGORIES`. User-defined categories would need a table instead.
- Dates and years: years are passed to functions as numbers, never read from "today" inside the core. Years of ISO dates are read in UTC (`getUTCFullYear`) so results do not depend on the time zone.
- Depreciation is parked for now (tricky to get right). A purchase counts fully in the year it was bought, which is also how a household thinks. Later, an optional lifespan can spread the price over several years (mostly a business concept), with the detailed German rules (AfA, thresholds for low-value assets).
- Business: a boolean flag on an item, not a category
- Money: plain euro numbers, no integer cents
- Database access: Drizzle (TypeScript schema, no code generation, `drizzle-kit` for migrations). The `CATEGORIES` array is reused for the category column so the list lives in one place.
- i18n: `@nuxtjs/i18n` with `en` (default) and `de`, strategy `no_prefix` (the URL does not change with the language). The locale is detected from the browser on the first visit (fallback `en`) and a manual choice is stored in a cookie (`detectBrowserLanguage` with `useCookie`); the language switcher calls `setLocale()` instead of navigating. Locale files are `i18n/locales/en.json` and `de.json`; category and interval names are keyed by their ids (`category.housing`, `interval.monthly`). Nuxt UI's own texts (modal close button, empty table) follow the i18n locale on their own, because the Nuxt UI module provides its locale from `$i18n.locale`, so `UApp` needs no `locale` prop. `@nuxtjs/i18n` does not set the document language, so `app.vue` sets `<html lang>` (the locale code) and `dir="ltr"` with `useHead`; a right-to-left language would need `dir` from the locale.
- `RecurringCost` and `Purchase` each carry a `kind` discriminant (`'recurring'` / `'purchase'`), and `type Cost = RecurringCost | Purchase`. No separate entry type for the monthly list. Test helpers set `kind` by default.
- Yearly and quarterly recurring costs get a `dueMonth` (1-12), a month only, not a full date. A yearly cost falls in that month every year; a quarterly cost starts in that month and repeats every 3 months (`dueMonth: 2` means February, May, August, November). `'quarterly'` is added to `Interval` (`PERIODS_PER_YEAR` gets `quarterly: 4`). `MONTHS` and `Month` are derived from a const array. `RecurringCost` is a union type: a monthly cost has no `dueMonth`, a yearly or quarterly cost must have one (the compiler enforces it). Currently `dueMonth?: Month` is still optional until the union is in place.
- With the union type a yearly or quarterly cost always has a `dueMonth`. Data that reaches the core without one (untyped input, old rows) is skipped in the monthly views (`monthlyTotals`, `costsInMonth`) but still counts in the annual totals, so the API must validate that `dueMonth` is present for those intervals.
- API: REST routes per resource, `GET`/`POST` on `/api/<resource>` and `PATCH`/`DELETE` on `/api/<resource>/[id]`. Routes stay thin: validate with Zod (`readValidatedBody`, `getValidatedRouterParams`), call a function in `server/utils/costs.ts`, return the result. All schemas live in `shared/utils/validation.ts`; the shared `idParamsSchema` coerces the id from the URL (400 on an invalid id). The list routes return rows ordered by `id`, so a row keeps its place after an edit (the page then sorts the combined table by name, see Pages and views).
- Status codes: invalid input 400 (Zod issues in the body), unknown id 404, successful `DELETE` 204 without a body, `PATCH` returns the updated item with 200.
- PATCH: body is a partial of the create fields (`patchRecurringCostSchema`, `patchPurchaseSchema`), an empty patch is rejected. For recurring costs `interval` and `dueMonth` can change; `updateRecurringCost` loads the stored row, merges the patch, validates the result with `createRecurringCostSchema` (400 if e.g. a yearly cost has no `dueMonth`) and writes `dueMonth: null` when the result is monthly, so no stale month stays behind. The 400 is thrown inside the util function.
- Row ids in the UI: `Cost` and the other core types have no `id` (the API sends it at runtime). Edit and delete will use a wrapper type such as `Stored<T> = T & { id: number }` for data from the API, so the core types and their tests stay id-free. Implemented: `Stored<T>` is in `shared/types/calculation.ts`; `costs.vue` types the fetched rows as `Stored<...>`.
- Dashboard money and year: amounts on the dashboard are shown in whole euros (`useMoney()`), while the costs table keeps cents. The calculation stays exact and only the display is rounded, so household plus business can differ from the total by 1 on screen. Today's year and month are read once in `useYear()` (one `Date`, in UTC) and kept in `useState`, so the server and the browser agree about them around New Year and the two can never come from different moments (`currentYear`, `currentMonth`). Month names and labels such as "October 2026" come from `useMonth()` (`Intl`, UTC dates), not from copies in the pages. The selected year (`year`) is shared state too, so it survives navigation and a later costs page (#10) can read the same value. `YearSelect` (a `v-model` component with a translated, visible label) offers `availableYears(purchases, currentYear)`: the current year plus the years of all purchases, newest first. Known limits: recurring costs have no start or end date, so a past year shows today's recurring costs until price history exists (#23). A stored year that is no longer in the list (for example after deleting the last purchase of that year) falls back to the current year (#30): the dashboard computes `shownYear` (`years.includes(year) ? year : currentYear`) and uses it for the select, the sections, the month links and the headings, while the stored year stays unchanged, so it returns by itself when purchases of that year exist again and a list that is still loading does not reset it.
- Colour scheme (#50, steps 1 to 3): the active design direction is Cobalt (`mockups/cobalt`, git-ignored, so not in the repository; the teal direction is parked). It is applied by CSS only, in `app/assets/css/main.css`, by setting Nuxt UI's variables: `--ui-color-primary-50..950` (cobalt, `--ui-primary` is `#2D4BD8` in light and `#3B5BEB` in dark), `--ui-secondary` (the business orange, `#B54708` in light and `#FDBA74` in dark, used by the business badge and the split bar), `--ui-error` (`#B42318` light, `#F97066` dark) and `--ui-warning` (`#DC6803` light, `#F59E0B` dark), and the greys and borders (`--ui-bg*`, `--ui-text*`, `--ui-border*`) in the navy tones of the mocks, with a `.dark` block for "Cobalt midnight". `--ui-radius` is `0.75rem`, so fields and buttons get 18 px and cards 24 px (Nuxt UI's `md` is 1.5 times and `lg` 2 times the base; the mocks use 16 and 28). The rules are unlayered, so they win over Nuxt UI's `@layer theme` defaults. In dark mode `--ui-text-inverted` is white (white text on cobalt buttons), `.dark .text-primary` uses the light cobalt `#AFC0FF` and `.dark .text-error` the light red `#FCA5A5`, because the action colours are too dark for text on navy, and `.dark .bg-error` keeps the deep red `#B42318` for a solid delete button. The text-dimmed colours and the light accented border are not in the mocks and were derived. Shape, type and layout follow the mocks with classes and CSS only, no new elements: `pill` (labelled buttons, at least 44 px, round) and `pill-icon` (44 px round icon buttons) in `main.css`; `:ui="{ base: ... }"` on every `UInput` and `USelect` (48 px, 16 px corners, filled with `bg-muted`, a transparent ring in light mode so the focus ring still shows, a lighter ring in dark mode) and `:ui="{ content: ... }"` on the dialogs (32 px corners, `bg-elevated`); the class `card` on every `UCard` (28 px corners, soft shadow instead of a ring, 28 px body padding, 20 px on phones); the form is a grid with 18 px between fields and the two buttons in one row (`class` on `UForm`). `main.css` also sets the font (`--font-sans: 'Manrope'`, which Nuxt UI's font module downloads at build time and serves from our own server), the heading scale (h1 30 px, h2 18 px, weight 800), the form label style (scoped to `labelWrapper`, because buttons use `data-slot="label"` too), 32 px above and 64 px below the page, 24 px between sections, 16 px below a section heading, and a container of 1160 px. The dashboard is laid out as flex rows with `:has(#this-month-title)` on the layout's container, because the sections sit directly in it and no wrapper element may be added: the heading and the year picker share the first row (picker to the right), "This month" (weight 3) sits next to the add tile (2), the categories (3) next to the split (2), and everything wraps into one column on narrow screens. The sr-only texts of the months chart are kept inside its scroll area with `relative`, which also removed the sideways page scroll at 320 px. Not done yet, because they need new elements (later steps of #50): the category badges with icons, the segmented type control, the business row of the form, the cobalt hero card, the phone layouts, the logo and favicon (`mockups/cobalt/brand`) and the dark field fill details; the delete red and the input border of the mocks are not applied outside the variables above.
- Category badge (#51): a disc with a white Lucide icon per category, colours as tokens `--category-<id>` in `main.css` (from the mocks), lookups in `useCategory()`. Dark-mode mobility (`#0284C7`) has 4.10:1 with white, below the 4.5:1 of the issue's acceptance criteria; the author keeps the mock's colour, because the icon is decoration (the name is always text) and only 3:1 applies. Not verified: whether the production build or the cluster needs internet access for the icons (Lucide is fetched remotely, not installed); check in the Docker and Kubernetes steps. Details in `documentation/frontend/colour-scheme.md`.
- Favicon and manifest (#58): the Cobalt icon set and a static `public/manifest.webmanifest` (no module, no service worker, so not an installable app, see #97); the links and two `theme-color` metas (light and dark through `prefers-color-scheme` media queries, so they follow the system, not the app's `.dark` class) are in `app.head` in `nuxt.config.ts`; the manifest has one name for both languages and no `display` field; the C2PA metadata was removed from the icon files.
- Bars and charts: lists with bars (costs by category, later the months) are hand-built, because every value must be real text for all users, the month bars have to be real links, and they should render without JavaScript. A chart library is only a candidate for trend charts, and would need to be evaluated for server rendering, keyboard and screen reader support first.

## Open decisions

- Depreciation: optional lifespan for purchases, evenly spread or per AfA rules (parked)
- Start and end dates for recurring costs: the direction is decided, a price history per cost (a list of amounts, each valid from a month) plus an optional end month, see issue #23. Until it exists, past years would show today's recurring costs, so the dashboard's year selector should offer only the current year
- Time handling: how dates and periods (month, year) are represented and queried (months are 1-12 in the API, array index 0 = January in `monthlyTotals`)
- Currency: euro only, or configurable
- State handling: plain composables or Pinia
- Postgres in k8s: own StatefulSet manifests, Helm chart, or an operator like CloudNativePG
- Manifest management: plain YAML, Kustomize or Helm
- Costs table and year: should the table be filtered by the selected year? Only purchases have a year, recurring costs have none
